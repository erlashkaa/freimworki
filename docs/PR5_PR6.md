# ПР5 и ПР6 — реализация и проверка

Дата проверки: 18 октября 2026 года.

Оба предоставленных файла «Технологии разработки приложений на базе
фреймворков (часть 1 из 2)» имеют одинаковый текст задания, различается номер.
Поэтому разработана одна веб-версия FinanceTracker, покрывающая их требования.

## Результаты проверок

- pytest: **45 тестов прошли**, включая 21 прежний тест ПР1–3.
- flake8: замечаний нет.
- `manage.py check`: замечаний нет.
- `manage.py makemigrations --check --dry-run`: модели соответствуют миграции.
- `manage.py check --deploy` с production-настройками: замечаний нет.
- Сборка статики через collectstatic выполнена.
- Проверка синтаксиса JavaScript через `node --check` выполнена.
- В браузере проверены регистрация, категория с лимитом, расход,
  превышение лимита, отмена, изменение лимита, перезагрузка, выход и вход.
- Временные тестовые данные не записывались в старые data/*.json.

### Измерение кэширования

Тест с `django_assert_num_queries` подтверждает: первое получение сводки
вызывает 5 запросов к БД, повторное — 1 запрос версии данных. Это уменьшение
числа запросов к БД на 80% в данном сценарии. Создание и отмена операции,
изменение категории инвалидируют результат сменой версии. Кэш разных
пользователей проверен отдельно.

### Нагрузочная проверка

Конфигурация: Windows, Python 3.14, Django 5.2.18, SQLite,
Waitress 3.0.2, один процесс, четыре серверных потока, localhost.
Перед измерением создано 20 операций отдельного тестового пользователя.
Запросы чередуют сводку и историю; проверяется не только HTTP 200,
но и ожидаемая сумма/число записей.

| Показатель | Значение |
|---|---|
| Запросов в измеряемой фазе | 200 |
| Параллельных клиентов | 8 |
| Ошибок | 0 |
| Общее время | 57,268 с |
| Запросов в секунду | 3,49 |
| Медиана задержки | 2225,90 мс |
| 95-й процентиль | 3282,13 мс |

Результат относится к текущему компьютеру и клиенту urllib; это учебная
проверка корректности под параллельными запросами, а не подтверждение высокой
производительности. Одновременная интенсивная запись и публичная инфраструктура
этим сценарием не проверялись. Для повторения используется команда из
docs/DEPLOYMENT.md. Исходный локальный результат: build/load-test.json.

## Что показать на защите

1. Запустить `python serve.py`, открыть http://127.0.0.1:8765.
2. Зарегистрироваться, создать категорию с месячным лимитом.
3. Добавить доход и расход, показать баланс и остаток лимита.
4. Изменить месяц, категорию фильтра и сортировку истории.
5. Отменить расход: запись остаётся, баланс и лимит пересчитываются.
6. Перезагрузить страницу: данные и сессия сохраняются.
7. Выйти и создать второй аккаунт: чужие категории и операции не видны.
8. Открыть DevTools → Network и показать JSON-запросы `/api/`.
9. Показать документацию API, модели, формы, кэш и результаты тестов.

Для ПР5 удобно сначала показать сервер, API и клиентскую интеграцию;
для ПР6 — безопасность, оптимизацию, тестирование и развёртывание.
Это порядок демонстрации: сами документы не разделяют требования таким образом.

## Границы реализации

Приложение развёрнуто и проверено локально. Внешний домен и публичный сервер
не подключались. Production-настройки проверены программно; TLS-прокси
нужно настроить при выборе реального сервера. Ограничения SQLite, локального
кэша и лимитера за прокси описаны в docs/DEPLOYMENT.md.

Веб-версия хранит данные в SQLite, CLI и Tkinter — в JSON. Для переноса есть
команда import_json; синхронизации двух хранилищ в реальном времени нет.
